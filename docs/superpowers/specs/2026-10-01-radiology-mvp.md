# متطلبات تطوير Scan4Dent

المصدر: طلب المستخدم بتاريخ 2026-10-01، بعنوان «تعديلات نظام إدارة مركز الأشعة»، والأقسام العشرون الواردة فيه. هذا المستند يثبت نطاق التنفيذ والقرارات المقترحة؛ الأسئلة المفتوحة أدناه تحتاج إجابات المستخدم قبل اعتماد تفاصيلها.

## نطاق الـMVP

1. إجراء التسجيل الرئيسي الوحيد «حالة جديدة»: إنشاء الحالة أو تعديلها أو حذفها، اختيار مريض موجود والبحث عن تاريخه أو إنشاء مريض ضمن نفس النموذج. بيانات التسجيل اختيارية قدر الإمكان، والهاتف اختياري.
2. قسم «المرضى»: ملف المريض يشمل الاسم والهاتف إن وجد والعمر وسنة الميلاد والملاحظات، والحالات السابقة والفحوصات والملفات والفيديوهات وروابط المشاركة المرتبطة بالحالات.
3. حقلان للعمر وسنة الميلاد، يتحدث أحدهما عند تعديل الآخر. الحساب تقريبي باستخدام السنة الحالية؛ تخزين 01/01/السنة عند الحاجة فقط، مع إمكان تعديل المدخلين. بيانات الميلاد الكاملة السابقة لا يعاد كتابتها لمجرد فتح النموذج.
4. Dashboard: حالات اليوم، إجمالي الحالات، المرضى، الجديدة والمكتملة وقيد التنفيذ، توزيع الفروع والفحوصات، المستخدمون، الأطباء، الزيارات، وملخص مالي وفق الصلاحيات.
5. عزل بيانات الفروع: المرضى والحالات والمستخدمون والفنيون والأطباء وحسابات الفرع وإيراداته وفحوصاته وأسعاره وإحصاءاته. المدير يرى جميع الفروع، والمستخدم يمكن ربطه بفرع.
6. أنواع الفحوصات: الاسم، السعر الأساسي، الوصف الاختياري، التفعيل. يظهر السعر عند اختيار الفحص. أمثلة توضيحية: Panorama = 500 وCBCT = 1000؛ ليست أسعارًا تعتمد تلقائيًا على البيانات الحالية.
7. تسعير الحالة: السعر الأساسي والخصم والسعر النهائي وسبب الخصم ومن طبقه وتاريخ التعديل. تغيير سعر القائمة لا يغير الحالات السابقة. مثال: 1000 ثم 500 بسبب «خصم خاص للدكتور حسب الاتفاق.»
8. الحسابات: حسابات اليوم والفرع، الإيرادات والخصومات وعدد الفحوصات وتوزيعها والمبالغ والتقارير اليومية والشهرية.
9. أربعة أدوار فقط: Manager، Reception، Doctor، Technician. يسمح بتعدد المديرين.
10. صلاحيات تفصيلية داخل الأدوار: عرض/إنشاء/تعديل/حذف الحالة، رفع الملفات، عرض الحسابات، الخصومات، إدارة المستخدمين والزيارات والفروع والفحوصات، مع تخصيصات لكل مستخدم.
11. المدير: إدارة النظام كله والحسابات الكاملة. الاستقبال: التسجيل والتعديل والرفع والمشاركة ومتابعة الحالات، وحسابات يوم عمله أو فرعه المصرح به فقط. الطبيب: الحالات المصرح بها والبيانات الطبية والملفات والتقارير والملاحظات الطبية. الفني: الحالات المسندة إليه، التقدم والملاحظات الفنية والرفع والإكمال. الحسابات محجوبة تمامًا عن الطبيب والفني.
12. Google Drive مخزن الملفات الرئيسي الجديد؛ الرفع من داخل النظام، دون تكرار العمل يدويًا على Drive.
13. ملفات الحالة: صور، PDF، تقارير، ZIP/DICOM، طلبات الطبيب، فيديو، من واجهة موحدة.
14. فيديو: رفع مباشر عبر النظام إلى Drive ثم عرض/تحميل أو Preview حسب التنسيق وإمكانات الخدمة.
15. مجلدات Drive: Radiology Center / Branch / Year / Patient / Case، وتصنيفات Images، Reports، DICOM، Videos، Requests. يضاف رقم المريض/الحالة للاسم لمنع تعارض الأسماء المتكررة.
16. تدفق MVP في اتجاه واحد System → Drive. المزامنة مع ملفات مضافة يدويًا إلى Drive مؤجلة.
17. زيارات الأطباء: الطبيب والفرع ومسؤول الزيارة وتاريخ آخر/الزيارة القادمة والتعليق والاتفاق والملاحظات. Dashboard للزيارات الشهرية والمتأخرة وغير المزارة وعدد الزيارات. بلا صور.
18. Audit Log: إنشاء/تعديل/حذف الحالة، تغير السعر والخصم، رفع/حذف الملف، هوية المنفذ وتاريخ ووقت التنفيذ. سجل مركزي قابل للتصفية.
19. Soft Delete واسترجاع للمدير للحالات والملفات والمرضى. الحذف العادي لا يتلف الملف أو سجل الحسابات.
20. MVP قابل للتوسعة؛ التقارير المتقدمة وAutomations والإشعارات وWhatsApp API والمزامنة المتقدمة وتطبيق الهاتف وتطوير Workflow مؤجلة.

## قرارات مقترحة للمراجعة

- الإبقاء على Laravel 13 / Livewire 4 / Flux / Tailwind 4 وواجهة عربية RTL.
- أسماء الأدوار الخارجية أربعة كما طلب المستخدم؛ ترحيل قيمة `admin` الحالية إلى `manager` بترحيل بيانات متوافق، دون إنشاء دور خامس.
- فصل حالة سير الفحص (`new`, `in_progress`, `completed`) عن حالة المشاركة الحالية (`incomplete`, `ready`, `shared`, `opened`, `archived`).
- الفرع يتحدد تلقائيًا من المستخدم، ويختاره المدير عند التسجيل. وجود فرع محدد شرط داخلي للعزل، وليس حقلاً يعاد إدخاله عند كل حالة.
- إنشاء مريض مؤقت موسوم «بيانات المريض غير مكتملة» مع رقم ملف مستقل إذا ترك الاسم فارغًا؛ لا يعاد استخدام مريض وهمي واحد لجميع الحالات. الطبيب والفحص والهاتف والجنس والعمر والملاحظات اختيارية عند إنشاء المسودة.
- لا يلزم طلب «ملف تقرير» حتى تعتبر الحالة مكتملة؛ الفني/المدير يحدد حالة الفحص صراحة.
- سجل مالي مستقل يحفظ تاريخ الأسعار والتحصيل. الحالات القديمة ذات سعر غير معروف تظل «غير مسعّرة»، ولا تتحول إلى إيرادات صفرية مضللة.
- يوم العمل حسب `config('app.timezone')` الحالية؛ تغيير المنطقة أو اعتماد ورديات تعبر منتصف الليل قرار مستقل.
- روابط المشاركة صفحات النظام الآمنة؛ تعرض الملفات النشطة المحددة للحالة وتحدث بعد إضافة/حذف الملفات. لا تصبح ملفات Drive عامة.

## الأسئلة المفتوحة المرسلة للمستخدم

1. هل الطبيب يرى الحالات المسندة إليه فقط أم جميع حالات فرعه؟ المقترح: الحالات المسندة إليه فقط، كما يعمل النظام الحالي.
2. هل الإيرادات هي المقبوض الفعلي، مع الدفعات الجزئية والمتبقي، أم السعر النهائي للحالات فقط؟ المقترح: عرض الفواتير والمقبوض والمتبقي كقيم مختلفة؛ لا تسمية غير المقبوض «إيرادات».
3. هل تخزين المركز Gmail عادي أم Google Workspace مع Shared Drive؟ يؤثر على طريقة المصادقة والتخزين؛ لا تطلب المفاتيح أو كلمات المرور في المحادثة.
4. العملة الافتراضية تعتمد من إعدادات المركز قبل تسجيل أسعار فعلية. أمثلة المستخدم لا تحدد العملة.

## ما يحتاج تجهيزًا خارجيًا

- تفعيل Drive API وتهيئة OAuth client أو هوية Shared Drive وفق نوع الحساب. ربط الحساب يتم من واجهة المدير بعد تجهيز بيانات التطبيق في إعدادات البيئة.
- تجربة الرفع الحقيقي إلى Drive تتطلب حساب المركز وتهيئة الاتصال؛ لا تعتبر المحاكاة دليلاً على نجاح الاتصال الفعلي.
- Laravel queue worker وscheduler لرفع الملفات الكبير وإعادة المحاولة وتنظيف الأجزاء المؤقتة.

## مراجع التكامل

- Google Drive: https://developers.google.com/workspace/drive/api/guides/manage-uploads — resumable uploads للملفات الكبيرة.
- Shared Drive: https://developers.google.com/workspace/drive/api/guides/about-shareddrives — حسابات الخدمة لا تملك حصة تخزين شخصية أو ملكية ملفات؛ Shared Drive أو OAuth باسم مستخدم مناسب حسب حساب المركز.
